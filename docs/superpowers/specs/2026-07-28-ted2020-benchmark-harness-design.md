# 설계 — TED2020 벤치마크 코퍼스와 Tier 0 측정 하네스

> 작성일: 2026-07-28 (KST)
> 상태: 설계 확정 (구현 계획 대기)
> 닫는 질문: [요구사항정의서](../../요구사항정의서.md) §12 Q4(부분) · [AI 자막검수 오픈소스 비교](../../AI_자막검수_오픈소스_비교.md) §5 #2(핵심부)

## 1. 목적

[요구사항정의서](../../요구사항정의서.md) §9.1이 정의한 **Recall @ Budget**(검수 예산 X%에서의 오류 포착률)의
첫 실측치를 만든다. 이 숫자와 **무작위 베이스라인 대비 배수**가 README 최상단에 들어가며,
§11 R4("OpenAI 래퍼로 인식됨")에 대한 유일한 반증 자료다.

측정 대상은 **Tier 0(무료 결정론적 신호)만**이다. Tier 1(자가일관성)은 이 측정의 결과를 입력으로
받는 다음 단계다 — §4가 "Tier 1은 Tier 0가 좁힌 후보에만 적용"이라고 정의했으므로,
Tier 0의 선별 성능을 모르면 Tier 1에 무엇을 먹일지 정할 수 없다.

### 1.1 이 설계가 답하지 않는 것

- **Q4 전체** — 자가일관성 유사도를 편집거리로 잴 수 있는가는 LLM 재번역이 필요하므로 다음 단계다.
- **QE 모델(Tier 2)과의 비교** — v0.2 범위다.
- **실제 오류와 합성 오류의 일치도** — §9.2가 이미 한계로 명시했다. 2차 인간 평가 세트는 별도 과제다.

## 2. 전체 구조

측정은 5단계 파이프라인이며, 그중 ④만 제품 코드다.

```text
① fetch    OPUS TED2020 → 로컬 캐시 + manifest(SHA-256)     scripts/
② build    문장 쌍 → 타임코드 합성 → 깨끗한 자막 트랙        bench/
③ inject   오류 7종 주입 + 정답 라벨 생성                    bench/
④ measure  signals → risk → triage                          src/cuesift/  ← 제품
⑤ report   Recall@Budget · 베이스라인 대비 배수              bench/
```

**벤치는 제품 모듈의 첫 소비자일 뿐, 자체 판정 로직을 갖지 않는다.**
벤치가 자기만의 신호 계산을 가지는 순간 "측정한 것"과 "출시하는 것"이 갈라진다.

### 2.1 신설 제품 모듈

모두 §7.2가 "순수"로 규정한 모듈이다. 네트워크·LLM 의존이 없다.

| 모듈 | 책임 | 근거 FR |
| --- | --- | --- |
| `segment/` | Segment 데이터 모델 | §7.3 |
| `spec/` | 규격 프로파일 로드·검사 | FR-5.1 ~ FR-5.3 |
| `glossary/` | 용어집 로드·위반 판정 | FR-3.7 |
| `signals/` | Tier 0 수집기 8종 + 플러그인 인터페이스 | FR-3.1 ~ FR-3.8, FR-6.5 |
| `risk/` | 신호 융합 + hard fail 우회 | FR-6.1, FR-6.2 |
| `triage/` | 예산·임계값 선별 | FR-6.3 |

### 2.2 배치

벤치 코드는 최상위 `bench/`에 둔다. `pyproject.toml`의 `packages = ["src/cuesift"]`가
휠 포함 범위를 이미 제한하므로 별도 제외 설정이 필요 없다.
코퍼스 획득 스크립트는 기존 관례에 따라 `scripts/`에 둔다.

## 3. ① fetch — 코퍼스 획득

### 3.1 대상

OPUS TED2020 v1의 moses 배포본. 언어쌍 디렉터리명은 알파벳순이므로 **`en-ko`와 `ja-ko`** 다
(`ko-en`이 아니다 — 구현 시 실제 URL로 확인한다).

### 3.2 라이선스 제약

TED2020은 **CC BY-NC-ND 4.0**이다. 파생물 배포가 금지되므로 **코퍼스 원본도, 가공한 트랙도
리포지토리에 커밋하지 않는다.** §11 R6(저작권)과 같은 판단이다.

- 원본은 `data/ted2020/`에 받는다 (`.gitignore`).
- 가공 산출물은 `data/bench/`에 둔다 (`.gitignore`).
- **리포에 커밋하는 것은 `bench/manifest.json`뿐**이다.

### 3.3 manifest

```json
{
  "pair": "en-ko",
  "url": "...",
  "sha256": "...",
  "bytes": 0,
  "lines": 0,
  "retrieved": "2026-07-28",
  "license": "CC BY-NC-ND 4.0"
}
```

- manifest가 없는 첫 실행은 **기록 모드**, 있으면 **검증 모드**다.
- 로컬 파일의 SHA-256이 manifest와 일치하면 다운로드를 건너뛴다.
- 불일치하면 종료 코드 1. 조용히 다른 데이터로 측정하는 일을 막는다.

### 3.4 구현 제약

표준 라이브러리(`urllib`·`zipfile`·`hashlib`)만 쓴다. `scripts/check_links.py`가 세운 선례이며,
현재 본 의존성이 4개뿐인 상태를 유지한다.

## 4. ② build — 자막 트랙 합성

`bench/build_track.py`. 문장 쌍을 타임코드가 붙은 자막 트랙으로 바꾼다.

### 4.1 표본

- 시드 고정, 언어쌍당 **5000 세그먼트**.
- Tier 0는 LLM 호출이 없어 실행이 수 초다. 표본을 키우는 비용이 사실상 0이다.
- 주입률 10%면 오류 500건이고, Recall 추정 표준오차가 약 2%p다.

### 4.2 타임코드 합성

FR-2.4가 "번역이 타임코드를 보존한다"고 규정하므로 **시간은 원문(ko)에 붙고 en·ja가 물려받는다.**
그런데 같은 시간에 en은 42자, ja는 13자 제한을 받으므로, ko 기준으로만 정하면
번역 쪽에 규격 위반이 무작위로 섞여 들어와 측정이 오염된다.

그래서 duration을 **세 언어가 모두 만족하는 최솟값**으로 잡는다.

```text
duration = clamp( max(len_ko/cps_ko, len_en/cps_en, len_ja/cps_ja) × 여유계수,
                  min_duration, max_duration )
```

- 줄당 한도를 넘는 텍스트는 2줄로 나눈다.
- `max_duration`으로도 세 언어를 만족시킬 수 없거나 2줄로도 담기지 않는 세그먼트는 **표본에서 제외**한다.
- 세그먼트 간 간격은 고정한다 (겹침 금지, FR-5.1).

**`specs/ted.yaml`은 언어별 절을 갖는다.** §8.3.1은 TED 기준을 "42자, 2줄, 21 CPS"로 요약했으나
이는 라틴 문자권 기준이며, 한국어·일본어에 그대로 적용하면 줄당 한도가 비현실적으로 느슨해진다.
Netflix 프로파일이 언어별로 분리돼 있는 것과 같은 이유로 TED 프로파일도 `ko`·`en`·`ja` 절을 두며,
**각 값의 출처는 1단계에서 TED 가이드로 확인해 주석에 명기한다**(§11 R8: 출처 없는 수치를 기본값으로 넣지 않는다).
확인 결과 TED가 특정 언어의 값을 명시하지 않으면 그 사실을 주석에 적고 라틴 기준을 문자 폭으로 환산해 쓴다.

결과는 **규격 위반 0건인 깨끗한 트랙**이다. 이후 검출되는 규격 위반은 100% 주입분이므로
오탐이 원리적으로 0이 된다.

### 4.3 필터

빈 문자열, 중복 쌍, 극단 길이비를 제거한다. 제거 건수를 사유별로 기록한다.

### 4.4 부수 산출물

**제외 건수 자체가 결과다.** "ko 자막을 그대로 en·ja로 옮겼을 때 몇 %가 물리적으로 규격을
만족시킬 수 없는가"는 자막 현업에서 재분절이 왜 필요한지를 보여주는 숫자이며,
FR-5.4(v0.2 규격 자동 교정)를 정량적으로 정당화한다.

## 5. ③ inject — 오류 주입

`bench/inject.py`.

### 5.1 문서 불일치 해소

§4 설계 근거와 §9.2 벤치마크 전략이 서로 다른 오류 목록을 들고 있다.

- §4: 미번역 잔존 · **빈 출력** · **반복 붕괴** · 숫자 누락 · 규격 초과
- §9.2: 숫자 변조 · **용어 위반** · **의미 반전** · 규격 초과 · 미번역

겹치는 것은 3종뿐이고, 어느 쪽도 §5.3의 Tier 0 신호 8종을 덮지 못한다.
**주입하지 않은 신호는 Recall에 기여할 기회가 없으므로**, 목록 하나만 따르면
구현한 검출기의 절반이 측정에서 논다.

**두 목록의 합집합(7종)을 주입한다.** 주입기는 레지스트리 구조라 유형 하나가 수십 줄이다.

### 5.2 주입 유형과 FR 대응

| # | 주입 유형 | 방법 | 검출 담당 | hard fail |
| --- | --- | --- | --- | --- |
| 1 | 미번역 | 번역문을 ko 원문으로 치환 (전체 또는 일부 절) | FR-3.1 | ✔ |
| 2 | 빈 값 | 번역문을 빈 문자열·공백으로 치환 | FR-3.2 | ✔ |
| 3 | 반복 붕괴 | 마지막 어절을 3~8회 반복 | FR-3.3 | ✔ |
| 4 | 숫자 변조 | 번역문의 숫자 1개를 다른 값으로 변경 또는 삭제 | FR-3.4 | ✔ |
| 5 | 용어 위반 | 용어집 대응어를 비등재 표현으로 치환 | FR-3.7 | ✘ |
| 6 | 규격 초과 | duration 축소(CPS 초과) 또는 텍스트 확장(줄 길이 초과) | FR-3.8 | ✘ |
| 7 | 의미 반전 | 부정 표현 삽입·삭제 | **없음** | — |

### 5.3 제외 2건과 사유

- **FR-3.5 태그·서식 손실** — TED2020은 평문이라 마크업이 없다. 태그를 인위적으로 심으면
  주입과 검출이 같은 가정을 공유해 측정이 자기 충족적이 된다.
  검출기는 구현하되 이번 측정에서 빼고 **리포트에 미측정으로 표기**한다.
- **FR-3.6 길이비 이상치** — 전용 주입 유형이 아니라 다른 오류의 부수 효과다
  (미번역·빈값·반복이 모두 길이비를 깨뜨린다). 검출기는 켜 두고 기여도만 기록한다.

### 5.4 7번에 검출 담당이 없는 것은 오류가 아니다

부정어 하나가 뒤집힌 문장은 결정론적 코드로 원리상 구분되지 않는다.
**이 유형의 Recall이 0에 수렴하는 것이 Tier 1·QE 투자를 정당화하는 근거 숫자**이며,
이 측정의 부수 산출물이다.

### 5.5 주입 규칙

- **세그먼트당 최대 1개 오류.** 유형별 Recall이 정의되려면 라벨이 배타적이어야 한다.
- 주입률 기본 **10%**, 유형 간 균등 배분.
- 시드 고정. 같은 시드는 같은 오류 집합을 낸다 (NFR-3).
- **자격 검사** — 숫자 변조는 숫자가 있는 세그먼트에만, 용어 위반은 용어집 키가 있는
  세그먼트에만 적용한다. 자격 미달로 건너뛴 건수를 기록한다.
- **어떤 유형이든 실주입이 0건이면 실패**시킨다.

마지막 항목은 링크 체커에서 얻은 교훈의 직접 적용이다. "0 broken"이 통과로 읽혔던 것처럼,
**"용어 위반 Recall 100%"가 실은 "용어 위반을 1건도 주입 못 했음"일 수 있다.**
용어집이 비어 있으면 정확히 그렇게 된다.

### 5.6 용어집

`bench/glossary.ted.yaml`. **자동 후보 추출 + 수동 확정** 방식으로 만든다.

1. 코퍼스에서 고빈도 개념어를 기계적으로 뽑아 후보 목록을 만든다.
2. 사전적으로 대응이 명확한 30~50개를 사람이 확정한다.
3. 확정본만 커밋한다.

전자동 통계 정렬을 쓰지 않는 이유는, 오대응이 섞이면 **"용어집이 틀려서 생긴 오탐"과
"검출기 성능"을 구분할 수 없기 때문**이다. 코퍼스를 보지 않고 손으로만 적지 않는 이유는,
해당 용어가 코퍼스에 몇 번 등장하는지가 보장되지 않아 주입 건수가 부족해질 수 있기 때문이다.

### 5.7 산출물

- `data/bench/{pair}.injected.json` — 변조된 트랙
- `data/bench/{pair}.labels.json` — 정답 (세그먼트 ID, 오류 유형, 변조 상세)

## 6. ④ measure — 측정

`bench/measure.py`. 제품 모듈(`signals` → `risk` → `triage`)을 호출한다.

### 6.1 지표

| 지표 | 정의 |
| --- | --- |
| Recall@b | 예산 b에서 선별된 세그먼트가 포함한 오류 수 ÷ 전체 주입 오류 수 |
| 무작위 베이스라인 | 같은 비율을 무작위 선별. 기댓값은 b지만 **실측**한다 (시드 100회 반복 → 평균·표준편차) |
| 오라클 상한 | `min(1, b / 오류율)`. 완벽한 트리아지가 그 예산에서 낼 수 있는 최댓값 |
| 배수(lift) | Recall ÷ **실제 검수 비율** |
| 유형별 Recall | 오류 7종 각각의 포착률 |
| 신호별 기여도 | 신호를 하나씩 제거했을 때의 Recall 하락폭 (ablation) |

예산 스윕은 **1 · 2 · 5 · 10 · 20 · 30%**.

### 6.2 예산과 실제 검수 비율은 다르다

FR-6.2는 hard fail 신호가 가중합을 우회해 **무조건** 검수 큐에 들어간다고 규정한다.
주입 7종 중 4종이 hard fail이므로, 오류율 10%에서 hard fail만으로 이미 상당 비율이 큐에 들어간다.
이 상태에서 "예산 1%"를 요청해도 실제 검수 비율은 1%가 아니다.

그런데 Recall은 그 실제 비율을 쓴 결과로 계산된다.
**요청 예산으로 배수를 계산하면 숫자가 부풀려진다.**

따라서 리포트는 `요청 예산 / 실제 검수 비율 / Recall` 세 열을 **항상 함께** 내고,
배수는 반드시 실제 비율로 나눈다. README 최상단에 들어갈 숫자이므로
여기서 정직하지 않으면 프로젝트의 핵심 주장 자체가 무너진다.

### 6.3 가중치는 튜닝하지 않는다

FR-6.1의 신호 가중치는 **균등(무튜닝)으로 고정**하고 첫 숫자를 낸다.
같은 데이터에서 가중치를 맞추면 Recall이 부풀려지고 그 숫자는 새 데이터에서 재현되지 않는다.
튜닝이 필요하다면 그때 **분리된 검증 세트**를 만드는 것이 순서다.
첫 리포트에 "가중치 미튜닝"을 명시한다.

### 6.4 자기검증 불변식

측정 코드의 위험은 **틀린 숫자가 그럴듯해 보인다**는 것이다.
매 실행마다 4개 불변식을 검사하고, 위반 시 결과를 내지 않고 종료 코드 1로 실패한다.

| # | 불변식 | 위반이 뜻하는 것 |
| --- | --- | --- |
| 1 | Recall ≤ 오라클 상한 | 라벨 누수 — 검출기가 정답 파일을 보고 있다 |
| 2 | Recall(무작위) ≈ 실제 비율 (신뢰구간 내) | 선별·집계 로직 버그 |
| 3 | 예산 증가 시 Recall 비감소 (단조성) | 정렬·절단 로직 버그 |
| 4 | 주입 안 된 세그먼트의 hard fail = 0 | §9.1의 "hard-fail 오탐 ≈ 0" 목표가 깨졌다 |

4번은 §9.1이 목표로만 적어 둔 것을 실행 가능한 검사로 바꾼 것이다.
깨끗한 트랙에서 주입하지 않은 세그먼트가 hard fail을 받으면 정의상 오탐이다.

## 7. ⑤ report — 리포트

`bench/report.py`. `bench/results/{pair}-{date}.md`와 같은 이름의 `.json`을 낸다.

헤더에 재현 정보를 박는다.

```text
시드 · manifest SHA-256 · 코드 커밋 해시 · 표본 수
· 제외 건수와 사유 · 유형별 실주입 건수 · 미측정 신호 목록(FR-3.5)
```

마지막 두 줄이 **"무엇을 대상으로 통과했나"** 의 적용이다.
`Recall@10% = 0.62`만 적힌 리포트는 몇 달 뒤 자기 자신조차 검증할 수 없다.
**재현 불가능한 벤치마크 숫자는 없는 것보다 나쁘다 — 인용되기 때문이다.**

## 8. 검증 전략

§9.3의 테스트 계층을 따른다.

| 계층 | 대상 | 방식 |
| --- | --- | --- |
| 단위 | 신호 수집기 8종 · `spec` · `glossary` · `risk` · `triage` | 신호마다 양성·음성 케이스. 네트워크 없음 |
| 라운드트립 | 주입기 | 주입 후 실제 텍스트 차이가 라벨과 일치하는지. **라벨이 틀리면 모든 숫자가 틀린다** |
| 실패 경로 | 불변식·가드 | 검출기를 꺼서 해당 유형 Recall이 실제로 떨어지는지, 불변식 위반이 종료 코드 1을 내는지 |
| 벤치마크 | 전체 파이프라인 | 별도 실행, CI 비필수 (§9.3) |

**게이트를 만들면 반드시 실패시켜 본다.** 검사하지 않고 통과하는 게이트는 없는 게이트보다 나쁘다.
