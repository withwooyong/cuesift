## 0. 용어 풀이 — 먼저 개념부터

> 이 문서는 QE·MQM·화자분리 같은 약어를 전제하고 쓰였다. 처음 보는 사람도 §1부터 읽을 수 있도록 핵심 개념을 먼저 풀어 둔다. [TMS 비교 문서 §0](번역관리_TMS_솔루션_비교.md)이 **번역 관리** 어휘(TMS·TM·용어집)를 다룬다면, 이 문서는 **품질 측정** 어휘를 다룬다.

### QE와 트리아지란? — 이 문서의 두 축

**QE = Quality Estimation (품질추정)**

- **한 줄 정의**: **정답 번역 없이**, 원문과 번역문만 보고 "이 번역이 얼마나 믿을 만한가"를 점수로 추정하는 기술.
- **왜 중요한가**: BLEU 같은 전통 지표는 **사람이 만든 정답 번역(reference)** 과 대조해야 점수가 나온다. 그런데 운영 현장에 정답 번역이 있다면 애초에 번역할 필요가 없다. QE는 이 모순을 뚫는다 — **번역이 막 나온 그 시점에** 품질을 잴 수 있는 사실상 유일한 수단이다.
- **비유**: 정답지 없이 답안의 논리·문체만 보고 "이 답안은 위험해 보인다"를 골라내는 조교.

**트리아지 (Triage)**

- **한 줄 정의**: 응급실 **중증도 분류**에서 온 말. 여기서는 **위험도가 높은 자막 세그먼트만 사람 검수 큐로 보내는 것**.
- **왜 중요한가**: 이 프로젝트의 목표는 "번역을 더 잘하기"가 아니라 **"사람이 볼 양을 줄이기"** 다. 전량 검수(100%)를 표본 검수(5~10%)로 바꾸는 판단이 트리아지이고, 그 판단의 근거가 QE 점수다. → **QE는 재료, 트리아지는 제품.** §1이 "아무도 이 둘을 잇지 않았다"고 말하는 지점이 바로 여기다.

### 함께 나오는 핵심 용어

**① 음성·자막 생성** (§2 C 계층)

| 용어 | 풀이 |
|---|---|
| **STT** | Speech-to-Text, 음성 → 텍스트 전사. Whisper 계열이 사실상 표준 |
| **강제정렬 (Forced Alignment)** | 이미 아는 텍스트가 오디오의 **어느 시점에 발화됐는지** 맞춰 붙이는 것. WhisperX가 wav2vec2로 **단어 단위** 타임스탬프를 얻는 방식 |
| **화자분리 (Diarization)** | "누가 언제 말했는지" 구간을 나눠 화자 라벨을 붙이는 것. `pyannote`가 대표. 캐릭터별 말투 일관성(공백 ④)의 전제 |
| **WER** | Word Error Rate, 전사 오류율 = (삽입 + 삭제 + 치환) / 전체 단어 수. 낮을수록 정확 |
| **TTS** | Text-to-Speech, 텍스트 → 음성 합성. 더빙에 쓰인다 (§4에서 **범위 밖**으로 결정) |

**② 품질 측정** (§2 D 계층)

| 용어 | 풀이 |
|---|---|
| **정답 번역 (reference)** | 사람이 만든 기준 번역. 있으면 정확한 채점이 가능하지만 **운영 시점에는 존재하지 않는다** |
| **정답 번역 불필요 (reference-free)** | 정답 없이 점수를 내는 방식. §2 D 표의 "정답 번역 불필요 ✅"가 곧 **운영 투입 가능**을 뜻한다 |
| **MQM** | Multidimensional Quality Metrics. 번역 오류를 **유형 + 심각도**로 분류하는 산업 표준 체계. 심각도는 minor(사소) / major(중대) / critical(치명) |
| **오류 구간 (error span)** | 문장 전체 점수가 아니라 **"어디서부터 어디까지가 틀렸다"** 는 범위 지목. 검수자 화면의 하이라이트가 된다 |
| **DA** | Direct Assessment. 사람이 번역에 점수를 직접 매긴 평가 데이터. `wmt22-cometkiwi-da`의 `-da`가 이것 |
| **HTER** | Human-targeted Translation Edit Rate. 사람이 기계번역 결과를 고치는 데 **필요한 편집량** 비율 |
| **자가일관성 (self-consistency)** | 같은 원문을 **N회 번역해 결과가 얼마나 흔들리는지** 측정. 분산이 크면 모델이 확신 없다는 신호. QE 모델 없이 쓸 수 있는 경량 신호 |
| **역번역 (back-translation)** | 번역문을 **원문 언어로 되돌려** 원문과 유사도를 비교. 의미 이탈 탐지용 |
| **오픈웨이트 (open-weight)** | 모델 **가중치가 공개**되어 로컬 추론이 가능한 모델. 오픈소스 라이선스와는 별개 개념 |

**③ 자막 규격·포맷** (§2 E 계층)

| 용어 | 풀이 |
|---|---|
| **cue / 세그먼트** | 자막 한 블록 = **시작·종료 타임코드 + 텍스트**. WebVTT 표준 용어이며 프로젝트 이름 `cuesift`의 어원 |
| **타임코드** | 자막이 화면에 나타나고 사라지는 시각 |
| **CPS (읽기속도)** | Characters Per Second, 초당 글자 수. 너무 높으면 시청자가 못 읽는다. Subtitle Edit 기본값 **15 chars/sec** |
| **줄 분절 (line segmentation)** | 한 cue를 **몇 줄로, 어디서 끊을지**. 의미 단위로 끊지 않으면 읽기 어려워진다. 방송 규격은 보통 **최대 2줄** |
| **샷 체인지 (shot change)** | 영상 **컷이 바뀌는 지점**. 자막이 컷을 넘어가면 시청자가 같은 줄을 다시 읽게 되어 방송 규격에서 금기. 검출에 `PySceneDetect` 등이 필요(§5) |
| **SRT** | 가장 범용적인 구형 자막 포맷. 타임코드 + 텍스트만 담는다 |
| **WebVTT (.vtt)** | 웹(HTML5 `<track>`)·HLS 스트리밍의 **표준** 자막 포맷 → **OTT 자막의 핵심** |
| **ASS / SSA** | 위치·색상·폰트 등 **스타일 지정**이 가능한 포맷 |
| **TTML / IMSC1 / DFXP** | **방송용 timed-text** 계열. TTML은 W3C 표준, **IMSC1**은 방송·OTT 딜리버리용 TTML 프로파일, DFXP는 TTML의 구 명칭. §2 E에서 "상용 TMS가 하나도 지원하지 않는다"고 지적한 그 포맷군 |
| **EBU STL** | 유럽방송연맹(EBU)의 방송용 바이너리 자막 포맷(`.stl`). 유럽 딜리버리 요건 |

**④ 파이프라인 운영**

| 용어 | 풀이 |
|---|---|
| **CI 게이트** | 자동 파이프라인에서 **기준 미달 시 빌드를 실패시키는 검사 지점**. "GUI 도구는 CI에 넣을 수 없다"(§2 E)가 치명적인 이유 |
| **검수 큐** | 트리아지에서 "위험하다"고 판정된 세그먼트가 쌓여 사람이 처리하는 목록 |
| **★ (스타)** | GitHub 즐겨찾기 수. 프로젝트 **관심도의 대리 지표**이며 품질 보증은 아니다 |
| **Hunspell** | 오픈소스 맞춤법 검사 엔진. Subtitle Edit이 사용 |

## 1. 한눈에 — 결론

> **번역하는 도구는 널려 있다. 품질을 재는 도구도 (연구용으로) 있다. 그런데 이 둘을 잇고, 그 결과로 "사람이 볼 자막"을 골라내는 오픈소스는 없다.**

조사한 오픈소스는 5개 계층으로 깔끔하게 갈린다. 그리고 **계층 간이 끊겨 있다.**

| 계층 | 대표 오픈소스 | 성숙도 | 상태 |
|---|---|---|---|
| **A. 엔드투엔드 파이프라인** | VideoLingo, subsai, auto-subtitle-translate | 높음(VideoLingo 17.9k★) | ✅ 포화 |
| **B. LLM 자막 번역 전용** | LLM-Subtrans, ai-subtitle-translator, srt-llm-translator | 중간 | ✅ 포화 |
| **C. STT / 캡셔닝** | WhisperX, faster-whisper, whisply | 매우 높음 | ✅ 포화 |
| **D. 번역 품질추정(QE)** | COMET/CometKiwi, xCOMET, TransQuest, OpenKiwi | 높음(연구 성숙) | ⚠️ **연구용에 고립** |
| **E. 자막 규격 QA** | Subtitle Edit, pysubs2 | 높음 | ⚠️ **AI와 분리** |
| **🔴 F. QE → 트리아지 → 검수 큐 → CI** | **없음** | — | 🔴 **공백** |

**핵심 발견 3가지**

1. **번역 도구는 품질을 재지 않는다.** LLM-Subtrans(633★, MIT)는 8개 LLM 프로바이더를 지원하지만 **품질추정·신뢰도 점수·자막 규격 검증이 전무**하다(🟢 리포 확인). VideoLingo(17.9k★)는 Netflix 단일행 규격은 강제하지만 **명시적 human review 워크플로가 없다**(🟢).
2. **품질 측정 도구는 자막을 모른다.** COMET/CometKiwi(Apache-2.0, 770★)는 정답 번역 없이 점수를 낼 수 있지만(🟢), **문장 단위 MT 연구 도구**다. 타임코드·줄 분절·화자 개념이 없다.
3. **자막 QA 도구는 AI를 모른다.** Subtitle Edit는 `Fix Common Errors`·읽기속도 검사를 갖췄지만 **데스크톱 GUI 수작업 도구**이고, CI에 넣을 수 없다(🟡).

→ **비어 있는 자리 = "품질 점수를 근거로 검수 대상을 자동 선별하고, 그 결정을 CI 파이프라인에 태우는 계층".**

## 2. 계층별 상세 비교

### A. 엔드투엔드 파이프라인 — 이미 포화

| 프로젝트 | 라이선스 | ★ | 파이프라인 | QE/신뢰도 | 검수 트리아지 | 인터페이스 |
|---|---|---|---|---|---|---|
| **VideoLingo** 🟢 | Apache-2.0 | 17.9k | WhisperX → NLP/AI 분절 → **3단계 Translate-Reflect-Adaptation** → 정렬 → TTS 더빙 | ❌ (모델 선택으로 암묵 처리) | ❌ 없음 | Streamlit GUI, Docker, 배치 |
| **subsai** 🟡 | (확인 필요) | — | Whisper 계열 다중 백엔드 → 자막 생성 | ❌ | ❌ | WebUI + CLI + Python 패키지 |
| **auto-subtitle-translate** 🟡 | — | — | 생성 → 번역 → 영상 오버레이 | ❌ | ❌ | CLI |
| **open-whisperer** 🟡 | — | — | 오디오 추출 → 전사 → 번역 → muxing, **화자분리 포함** | ❌ | ❌ | CLI |
| **faster-auto-subtitle** 🟡 | — | — | faster-whisper → Opus-MT 번역 → 오버레이 | ❌ | ❌ | CLI |

**판단**: VideoLingo가 사실상 이 계층의 승자다. **여기서 정면 경쟁하면 안 된다.** 특히 더빙(TTS)까지 들어간 영역은 재현 비용이 크고 차별화가 없다.

**주목할 점**: VideoLingo의 `Translate-Reflect-Adaptation` 3단계는 사실상 **LLM 자가검수**다. 즉 "LLM으로 검수한다"는 아이디어는 이미 구현되어 있다. 그러나 **그 검수 결과를 정량화하지도, 사람에게 넘길 대상을 고르지도 않는다.** 이게 결정적 차이다.

### B. LLM 자막 번역 전용 — 포화, 그러나 얕음

| 프로젝트 | 라이선스 | ★ | 포맷 | 프로바이더 | QE/신뢰도 | 자막 규격 검증 | STT |
|---|---|---|---|---|---|---|---|
| **LLM-Subtrans** 🟢 | MIT | 633 | SRT · SSA/ASS · VTT | OpenRouter·Gemini·OpenAI·DeepSeek·Claude·Mistral·Azure·Bedrock | ❌ | ❌ | ❌ |
| **ai-subtitle-translator** 🟡 | — | — | SRT | OpenRouter 300+ 모델 | ❌ | ❌ | ❌ |
| **srt-llm-translator** 🟡 | — | — | SRT (타임스탬프 보존) | OpenAI·Gemini·Grok·OpenRouter | ❌ | ❌ | ❌ |
| **Batch Subtitle Translator** 🟡 | — | — | SRT·ASS·VTT·LRC | 17+ 프로바이더 | ❌ | ❌ | ❌ |

**판단**: 이 계층 전체가 **"LLM API 호출 + 자막 파싱"** 이고, 품질 축이 완전히 비어 있다. LLM-Subtrans는 `PySubtrans` 파이썬 패키지를 분리 제공하므로 **경쟁 대상이 아니라 재사용 후보**로 볼 수 있다(🟢).

> ⚠️ **여기가 우리 프로젝트가 빠지기 쉬운 함정이다.** 아무 설계 없이 시작하면 이 표의 5번째 행이 된다.

### C. STT / 캡셔닝 — 절대 직접 만들지 말 것

| 프로젝트 | 핵심 | 우리 프로젝트에서의 위치 |
|---|---|---|
| **WhisperX** 🟡 | faster-whisper + wav2vec2 강제정렬(**단어 단위 <100ms 타임스탬프**) + pyannote 화자분리 | **채택 후보 1순위.** 화자분리는 캐릭터 말투 일관성의 전제 |
| **faster-whisper** 🟡 | 경량·고속. pyannote 의존성·HF 토큰 불필요 | 화자분리 불필요한 경우의 대안 |
| **whisply** 🟡 | faster-whisper + mlx-whisper 배치 처리, whisperX/pyannote로 단어 단위 화자 주석 | 배치 운영 참고 |
| **gpt-4o-transcribe-diarize** 🟡 | OpenAI가 화자 라벨링된 `diarized_json` 반환 | API 경로 대안(비용·데이터 반출 검토 필요) |

**판단**: 이 계층은 **완전히 해결된 문제**다. 붙여 쓰면 된다. 단, [TMS 비교 문서](번역관리_TMS_솔루션_비교.md)에서 지적한 대로 **한국어 드라마(BGM·중첩발화·사투리) WER은 별도 검증이 필요**하다.

| **DeepSubQE** 🟡 | (논문) | — | 자막 번역 QE | ✅ |

`★ 이 표의 의미 ─────────────────────────────`
**xCOMET이 특히 중요하다.** 단순 점수(0~1)가 아니라 **"어느 구간이, 얼마나 심각하게 틀렸는지"** 를 MQM 심각도로 뱉는다(🟢 확인). 이건 그대로 **검수자에게 보여줄 하이라이트**가 된다. 검수자는 자막 전체를 읽는 게 아니라 **빨갛게 칠해진 구간만** 본다.

**SubER는 자막 전용 메트릭**이라는 점에서 유일하다 — 텍스트뿐 아니라 **타임코드와 줄 분절까지** 평가에 넣는다. 다만 정답 자막이 필요해서 운영 시점 트리아지에는 못 쓰고, **벤치마크 검증용**으로 쓸 수 있다.
`─────────────────────────────────────────────`

**판단**: 재료는 다 있다. **아무도 이걸 자막 파이프라인에 배선하지 않았을 뿐이다.**

**아무도 하지 않은 것 — 5가지**

| # | 공백 | 왜 아무도 안 했나 | 난이도 |
|---|---|---|---|
| ① | **다중 신호 융합 신뢰도** — QE 점수 + 자가일관성(N회 번역 분산) + 역번역 유사도 + 결정론적 위반 플래그를 하나의 위험도로 합성 | 번역 도구 개발자는 QE 연구를 모르고, QE 연구자는 자막 파이프라인을 안 만듦 | 중 |
| ② | **위험 기반 트리아지** — 임계값 위 세그먼트만 검수 큐로. "전량 검수 → 표본 검수" 전환의 실체 | 상용 TMS는 검수 시간을 줄일 **동기가 없음**(시트당 과금) | 중 |
| ③ | **자막 규격을 생성 시점에 보장** — 검사가 아니라 **번역 결과를 규격에 맞게 재분절·재타이밍** | LLM에게 프롬프트로 시키면 안 지켜짐. 결정론적 코드가 필요한데 다들 LLM에 맡김 | **상** |
| ④ | **화자별 말투 일관성** — 시리즈 전체에서 인물 어조·경어법 유지 | 문장 단위 번역 구조로는 불가능. 화자분리 + 캐릭터 시트 + 컨텍스트 관리 필요 | **상** |
| ⑤ | **CI 배선** — CLI + Git + 머신리더블 리포트 | GUI 도구(Subtitle Edit)와 GUI 파이프라인(VideoLingo)이 시장을 차지 | 하 |

**이 문서의 공백(정직하게)**

- 🟡 표기 항목(subsai·TransQuest·OpenKiwi·pysubs2·Subtitle Edit의 라이선스·스타·최신 릴리스)은 검색 결과 기반이며 **리포 직접 확인 미완료**. 다만 이 중 subsai·TransQuest·OpenKiwi는 §4에서 **채택 후보가 아니므로** 착수를 막지 않는다. **갱신(2026-08-01)**: pysubs2는 **동작을 실측했다**(#4 참고). 🟡가 남은 것은 라이선스·스타·릴리스 이력이지 기능이 아니다.
- **한국어 성능 미검증**: CometKiwi·xCOMET의 한국어 쌍 성능을 확인하지 못했다. **저자원 언어(th·vi·id)는 초기 범위에서 빠졌다** — Q2가 초기 언어쌍을 **ko→en/ja**로 확정했고, 공개 병렬 코퍼스가 풍부한 쪽에서 방법론을 먼저 검증한 뒤 확장한다. ko→en/ja에서도 QE 성능은 여전히 미검증이며, 요구사항정의서는 이를 리스크 **R2**로 등록하고 **v0.1을 QE 없이 설계**하는 것으로 대응했다 — QE는 Tier 2 플러그인이라 성능이 나쁘면 빼면 된다.

- **평가 데이터**: K-드라마 자막은 저작권 때문에 리포에 넣을 수 없다. → §9.2에서 **TED2020/OPUS + 합성 오류 주입**으로 확정됐고, 측정 오염을 막기 위해 벤치마크 전용 프로파일을 분리하기로 했다(Q5). **갱신(2026-07-29)**: 분리 결과는 단일 파일이 아니라 언어별 `specs/ted-ko.yaml`·`specs/ted-en.yaml`·`specs/ted-ja.yaml` 세 개다 — Netflix 프로파일과 마찬가지로 언어마다 CPS·자수 상한이 다르기 때문이다(§8.3 구조 참고).
- **샷 체인지 검출**: 공백 ③의 핵심인데 이번 조사에서 다루지 못했다(PySceneDetect 등). 해당 요구사항 `FR-5.5`가 **v0.3**으로 배치돼 당장의 차단 요인은 아니다.

6개 전부 **닫혔거나, 로드맵상 아직 시점이 아니거나, 의사결정에 쓰이지 않는다.** #2는 남의 리포지토리를 열어봐서 답이 나오는 질문이 아니었다 — ko→en/ja 병렬 코퍼스에 **합성 오류를 주입해 Recall@Budget을 실측**해 닫았다(§9.1·§9.2, 실측치는 위 #2 행).

**① TED2020 ko-en·ko-ja 확보 → ② 측정 하네스 작성 → ③ #2 해결까지 완료했다.** 다만 ③에서 **Q4는 함께 닫히지 않았다** — #2("경량 신호만으로 트리아지가 성립하는가")는 Tier 0 질문이고, Q4("자가일관성 유사도를 무엇으로 재는가")는 LLM 재번역이 있어야 답할 수 있는 Tier 1 질문이라 이 벤치의 측정 범위 밖이다. 이전 판(위 #2 행의 "정정" 참고)은 이 둘을 같은 실험으로 묶어 적었는데, 그것이 틀렸다. **Q4는 그 뒤 2026-09-04에 별도 spike로 닫혔다**(임베딩이 필요하다는 결론) — 실제로 두 질문이 서로 다른 실험을 요구했다는 것이 사후에 확인된 셈이다.

조사 질문을 적을 때 **"조사로 닫히는 것"과 "측정으로 닫히는 것"을 섞지 않는 편이 낫다.** 섞이면 측정해야 할 항목이 조사 목록에 묻혀 계속 미뤄진다 — #2가 실제로 그랬다. **같은 이유로 "같은 실험에서 같이 닫힌다"고 미리 단정하지 않는 편이 낫다** — 층이 다른 질문을 하나로 묶으면, 한쪽만 닫혔을 때 나머지도 닫힌 것처럼 읽힌다.
